# WorkoutFlex

Next.js 15 (App Router, Server Actions) + Supabase (Postgres, Auth, RLS) + Tailwind, deployed on Vercel. Used mostly on an iPhone mid-workout, so every change must work at 390px wide with 44px tap targets and 16px inputs.

## Architecture

- **Plan engine** (`lib/plan/`, pure TS, runs under `node --experimental-strip-types`): the plan is never stored. `generatePlan(settings)` rebuilds weeks → days → blocks from the profile. Template lines live in `templates.ts`.
- **Exercise database**, one source of truth:
  - `lib/plan/exercises.ts`: catalog of built-in exercises (`key`, `name`, `load`, `video`, template `lines`)
  - `lib/plan/videos.ts`: YouTube ids per video key (main + backup)
  - `lib/plan/muscles.ts`: muscle ids, groups, body-map shapes, and `EXERCISE_MUSCLES` per exercise key
  - `lib/plan/equipment.ts`: equipment ids (bodyweight, dumbbell, barbell, kettlebell, cable, machine, band, other) and `EXERCISE_EQUIPMENT` per exercise key, for the Library and swap filters
  - `lib/plan/catalog.ts`: joins the four into rows shaped like the Supabase `exercises` table
  - `scripts/sync-exercises.ts`: upserts those rows into Supabase. Runs before every `npm run build` (so every Vercel deploy) when `SUPABASE_SERVICE_ROLE_KEY` is set
  - Custom exercises people add in the Library tab are rows with `owner = auth.uid()`; the sync never touches them
- **Classes** (yoga, spin…): `logs.kind = 'class'`, the activity in `title` (migration 0014), logged from Today's "Log a class" sheet (`components/ClassSheet.tsx`, through the Dock) or the Log tab. Always extra work: `countsForDay` in `lib/types.ts` keeps them out of "day done" checks, and `classU` in `accountability.ts` scores them by time and effort as extra work.
- **Set logs** (`set_logs`) store `exercise_key`, never template text, plus `plan_date` when a session is done early. Set numbers are unique per date and exercise, not per workout: when two workouts with the same exercise are logged on one date, `SetRows` in `Sets.tsx` steps a day's rows around the numbers the other holds (`no`, `rowOf`), and `upsertSet` refuses a save that would replace another plan day's set. Count sets, never read meaning into `set_no`.
- **Extra work in the Score** (`accountability.ts`): `extra` in the result is what was logged beyond the plan (sets on any day, unplanned sessions), whether or not it scored; `parts.e` is the points. A day adds at most half its own plan (10 at least), a day off 30. It counts in full in a kept week (80%+), sliding to nothing at `EXTRA_FROM_PCT` (50%), and never in `NO_EXTRA` phases (time trial, taper, race), cutback weeks or when pain makes the plan ease off (4+; a 3/10 "hold" still counts). In recovery and return weeks (`NO_EXTRA_RUNS`) lifting, classes and walks count but extra running does not. On a run day, a second run or going 10%+ past the plan is extra; the same run by hand and from Health is one run. Progression logic (stalls, bests, suggested weights) is in `lib/plan/progress.ts`.
- **New people:** nothing before a person's first use counts against them. `app/page.tsx` sets the Score's `horizon` to the first thing they logged (or the day the account was made), and `consistency` in `ontrack.ts` starts from the first active date, so a plan start in the past or a mid-week sign-up never opens on missed days. Setup pre-fills the phone's time zone and the coming Monday and tracks no pain area until one is typed. `saveSettings` refuses a start that isn't a Monday and a time trial on Monday to Thursday. The time trial is on its own date when that is Friday to Sunday (`generate.ts`); a race takes its day and nothing is planned after it that week. A signed-in account with no profile row gets one from `ensure_profile()` (0020). "Set or change your password" in Settings is `setPassword`; `@mailinator.com` addresses can't be sent a sign-in link.
- **Reads that grow** go through `paged()` (`lib/supabase/paged.ts`): the API returns at most 1,000 rows a request whatever `.limit()` says, so logs, sets, sessions, skips, moves, swaps, copies and supersets are read a page at a time in a fixed order.
- **Wording follows the person.** `gatesFor(painAreas)` and `tracksKnee` in `lib/types.ts`, and `PlanSettings.painAreas` in the engine: knee tests and knee notes only for someone tracking a knee, plain wording otherwise. Gate keys (`stairs`, `bend`, `hop`) never change. Lifting done away from the gym is "(home)".
- **A run's weight in the Score** is `runUnits(b)`: `plannedMinutes(b)` (`intensity.ts`) / 2, never under 20, or 30 for the long run and tests.
- **Every rule is per profile.** Nothing may depend on one person's dates: anchor to the profile's start, time trial and race, and add a case to `PROFILES` in `plan.test.ts` when adding a rule.
  - `paces.ts`: training paces from the latest 5K/10K test (`fitness5k`), goal pace that finishes under the goal
  - `adapt.ts`: `planFor()` is the plan as shown everywhere (paces from tests, skips, then pain warnings and unpassed gates change the coming week)
  - Moves (`day_moves`, one row per workout moved within its Mon–Sun week) are applied in `generatePlan` before skips, so every view and the `.ics` feed see the moved days. `moveDay`/`catchUp` in `generate.ts` build a week's full move list; `arrange` refuses the time trial, the race, other weeks and back-to-back run-walk days. Logged days never move, so `set_logs.plan_date` stays correct
  - Exercise swaps (`exercise_swaps`, one row per template exercise done as another on one plan day) are keyed by `Block.planDate`, the plan's own date, so they follow moves and folds. `applySwaps` in `swaps.ts` runs last (in `planFor`, the `.ics` route and the AI check-in) and sets a `Block.swaps` overlay; template `items` never change, so use `itemLine`/`itemKey` to read a line as shown. Rows whose original or new exercise is gone are ignored. Logged sets are never re-keyed: sets under an exercise a day doesn't show are listed as "Also logged"
  - Supersets (`supersets`, migration 0017: one row per group holding its exercise keys, the template's key or an added exercise's, never a swapped-in one). Saved for the workout, not a date: `dayGroups` in `supersets.ts` shows a group on any day with two or more of its exercises (any rows, any lift block, added exercises too), so it follows moves, folds and swaps and comes back each week. Nothing is overlaid on the plan: `DayBlocks` groups the rows where they are (colour bar, A1/A2, the whole group open together), `editGroup` builds every change (a row leaving keeps the others together) and it goes through the Dock outbox as a `supersets` op with phone-made ids (`components/Superset.tsx`). `nextInRound` in `workout.ts` drives logging on set counts, never set numbers: no rest mid-round (and a running rest stops), the group's longest rest after the round with the timer's `Goto` on the row the next set is in. A template can come with pairs (`Block.supersets`, item indexes: the own-runs upper sessions and `LEGS.C_gym`): `daySupersets` puts them after the person's own, and a saved row with `off` (0018) switches one off, which is how "Remove from superset" works on them (nothing is deleted; Undo deletes the off row). The `.ics` feed and AI check-in ignore them; `superset_links` (0013) is unused
  - Day copies (`day_copies`, "Swap for another day": one plan day does another day's workout, anywhere in the program) are keyed by both plan dates (before moves) and applied in `generatePlan` before moves and skips, always from the template (no chains); `canCopy` refuses tests, the time trial, the race, past or logged days and run-walk clashes. A copy whose `planDate` the plan leaves free (a rest day) adds a day there instead (`Day.added`, "Add a workout"; `canAdd` also refuses a date whose own workout was moved away): it's never a planned day, so the Score counts what's logged there as extra work, and ontrack/missed/week counts skip it. An added day that repeats a day of the `MAKEUP_DAYS` (7) before it which wasn't finished is a make-up (`makeUpSource`, `makeUpDay`): the Score moves what's logged there onto that day, up to what it still asked for, so it ends where doing it on time would have, with no extra credit; only what's left over is extra. "Make up a missed workout" on Today's rest day lists the ones under `MAKEUP_MAX` (30%) done (`missedDays`, `doneShare`). `intensity.ts` scores each day (`dayIntensity`, `compareDays`): within `COPY_TOLERANCE` and the same kind of day is a match, otherwise the copied day's Score credit is multiplied by `fit.credit` (0.5–1). Saving a copy drops that day's exercise swaps
  - Own runs (`profiles.own_runs`, migration 0016: runs from another running plan, entered in Settings one per line or with `npm run own-runs`). From the week of the first to the week of the last, `generatePlan` replaces the week's days with `ownWeeks` (`ownruns.ts`) before copies, moves and skips, and the week's phase is `own`: the runs stay on their days, a run of `LONG_KM` (5.5) or more gets abs only, legs never fall the day before a run (one full session alone on a free day, `LEGS.short` after an easy short run), upper is twice a week on free days of its own (`UPPER.fullA` then `fullB` in turn, never a leg day, resting before a hard run where it can), up to `MAX_DAYS` (6) training days, and legs ease off around a race. `profiles.own_runs_from` (0018, set to today when a list is first saved) is the day of the switch: days before it keep the plan's own, so a week under way isn't rewritten; null takes the whole list. Weeks outside the list are the plan's own. These runs set `Block.hard` (read by `isHard`) and `Block.dist`, or `km` for the week's long run; the plan's own time trial or race inside those weeks stays as an anchor
  - `stats.ts`: the Stats tab's numbers (`strengthIndex`, `bestsByWeek`, `paceNeeded`): they move with weight, reps and times, never with how much was logged
  - `ontrack.ts`: the Today verdict, consistency, pain trend, wins. `ics.ts`: the calendar feed
- **Offline:** `components/Dock.tsx` is a per-user outbox (localStorage). Set, unset and session writes go through `send()`, which saves them on the phone with no signal and replays them in order. New write paths that run mid-workout should go through it too; anything else must catch network errors rather than throw. Replays hold a Web Lock so two tabs never send the same write; ops the server refuses on replay are kept and explained in `SyncSheet.tsx` (opened from the "not synced" banner after 2 min or 5 failed tries).
  - Every live load saves the Dashboard's props on the phone (`lib/offline.ts`, IndexedDB, one person, `CACHE_VERSION`: bump it when `DashboardProps` changes shape). `OfflineApp` renders from that copy on the "/" error screen and on `/offline`, with `OfflineBanner` probing `/api/ping` to go live again. `/login` and Sign out clear it.
  - `public/sw.js` (registered per build by `ServiceWorker.tsx` as `/sw.js?v=<build>`): network-first pages falling back to the cached static `/offline` page, cache-first `/_next/static` and fonts; never caches pages with data, RSC, POSTs, `/api`, `/auth`, `/cal` or `/login`. Push handlers live in `public/sw-push.js` (imported if present).
- **Sound:** only through `lib/audio.ts` (`tick`, `chime`, `celebrate`, `fanfare`, `prime`, `release`). It sets the iOS audio session to "ambient" so sounds mix with Apple Music/Spotify, and plays nothing where that API is missing. Never create or resume an `AudioContext`, `<audio>` or `<video>` on load or when the app returns to the screen: that stops the person's music.
- **Workout lock:** sets lock 12 h after a workout ends (`sessionState` in `lib/plan/workout.ts`, enforced by the server actions too). "Unlock to edit" sets `workout_sessions.unlocked_at` (migration 0015, Dock op `workout-unlock`), opening them for 12 h from then. Locked inputs are dimmed and can't be tapped or focused.
- **Rest timer:** `components/RestTimer.tsx` (provider + view), stored per person in localStorage so it shows on every page. No rest starts after the set that ticks off a day's last planned set (`finishesDay` in `workout.ts`); extra sets still rest. Each rest carries a `Goto` (plan day, exercise row, tab): tapping the timer, or "Next set" once it's over, switches tab (or goes back to "/") and the day's `DayBlocks` opens that exercise at its first unlogged set (sessionStorage `wf-goto` + a window event).
- **Hold timer:** `components/HoldTimer.tsx` counts down `READY_SEC` (5 s, "Get ready") before the hold; that phase never counts as held time.
- **Added exercises:** "+ Add exercise" on a day (the swap sheet in add mode) adds any Library exercise on top of the workout as extra work. A pick is kept on the phone (`wf-added:<plan date>`) until its first set; after that the sets keep it on the day everywhere (`addedKeys` in `workout.ts`, which also lists any other exercise logged on that day). Targets come from `addedTarget`.
- **Push:** `lib/push.ts` (`schedulePush`, `cancelPush`, `sendNow`), off unless `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT` are set. Waits up to `SLEEP_MAX_SEC` are sent by the scheduling request itself (`after()`); longer ones by `/api/push/due`, which pg_cron calls every minute (`supabase/push-cron.sql`, applied by hand). Handlers are in `public/sw-push.js`, imported by `public/sw.js`.
- **Token routes:** `/cal/<token>.ics` and `/api/health` use the anon key and call security-definer SQL functions (`calendar_feed`, `ingest_workout`) that look up a hashed per-user token from `user_tokens`. Never use the service role for them.
- **AI check-in:** `lib/coach/review.ts` via the AI Gateway (`anthropic/claude-sonnet-5.5`, string model id). Turned off (card hidden, action refuses) unless `AI_GATEWAY_API_KEY` is set, locally and on Vercel. Advice only: suggestions are filtered against the plan and applied by the person. Cached per week in `ai_reviews`.
- **UI**: `components/Dashboard.tsx` tabs → `TodayPanel`, `PlanPanel`/`WeekCard`/`DayView`, `LogPanel`, `ProgressPanel`, `LibraryPanel`. `components/Sets.tsx` holds set logging and the exercise sheet (muscle map + video + history), opened anywhere with `openHistory(key)`.

## Testing

- `test@mailinator.com` is the shared test account. Mailinator inboxes are public and this repo is public, so treat it as untrusted: never give it real data. `npm run seed:test` resets it to ~5 weeks of history (runs, a 5K test, lifting sets, a stalled `lat-pulldown` and a dropped `db-ohp` so both warnings show, a skipped day, a cutback week, two supersets on the next lifting day). The script refuses any non-`@mailinator.com` address.
- `automation@mailinator.com` is the demo account for the share video. `npm run seed:demo` (needs `DEMO_PASSWORD`) resets it to about 27 weeks of good-looking made-up history in pounds, with today's workout three sets from done, ready to film. Mailinator only. Making the video: `.claude/skills/demo-video/SKILL.md`.
- `npm run score-audit -- <email>` rebuilds one account's Score from live data, read-only: the extra work logged each day and whether it added points. `SCORE_COMPARE=<path to another copy of accountability.ts>` scores the same data with that copy too.
- Never run `next build` in this folder while `npm run dev` is running: both write `.next` and the dev server breaks. Build in a separate worktree instead (`npx next build` there skips the exercise sync).
- `lib/coach/review.test.ts` tests the AI check-in with `MockLanguageModelV4`; no key needed.

## Rules

- **Adding or changing an exercise:** follow `.claude/skills/add-exercise/SKILL.md`. Never rename an existing `key`: logged history is stored by it.
- **Schema changes:** add a new numbered file in `supabase/migrations/` (never edit an applied one), enable RLS with owner-only policies like the others, then `supabase db push`.
- `npm test`, `npx tsc --noEmit` and `npm run build` must pass before committing. The tests fail if a template line has no exercise, or an exercise has no video or muscles.
- Secrets: `SUPABASE_SERVICE_ROLE_KEY` is server/build-only. Never prefix it `NEXT_PUBLIC_` or import it in app code.
